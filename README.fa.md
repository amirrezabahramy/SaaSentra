# SaaSentra؛ داشبورد مدیریت SaaS

[English](README.md) · فارسی

این پروژه یک سرویس مدیریت SaaS بر پایه TanStack Start و Prisma است و امکاناتی
مانند مدیریت سرویس‌ها، مشتریان، پلن‌ها، اشتراک‌ها، پرداخت‌ها، فاکتورها،
entitlement، feature flag، لاگ‌های حسابرسی و چرخه عمر اشتراک را فراهم می‌کند.

## راهنمای پروژه

### این پروژه چه کاری انجام می‌دهد؟

این برنامه یک مرکز کنترل برای مالک یا اپراتور SaaS است؛ یعنی شخص یا شرکتی که
چند محصول یا وب‌سایت دارد. برای مثال:

- وب‌سایت رستوران یا کافه
- وب‌سایت فروش تجهیزات ورزشی
- فروشگاه اینترنتی لباس
- هر محصول یا سرویس آنلاین دیگر

هر محصول به‌عنوان یک **Service** در این داشبورد ثبت می‌شود. توسعه‌دهنده، وب‌سایت
را به API مربوط به entitlement متصل می‌کند. سپس مالک می‌تواند از داخل داشبورد
دسترسی مشتریان را کنترل کند. برای نمونه، اگر اشتراک یک مشتری غیرفعال شود،
وب‌سایت متصل پاسخ غیرفعال را دریافت می‌کند و می‌تواند دسترسی مشتری را محدود یا
مسدود کند.

رابط کاربری و داده‌های اصلی هر محصول در همان محصول باقی می‌ماند؛ این پروژه فقط
مرکز مدیریت دسترسی، اشتراک و پرداخت است.

### مفاهیم اصلی

- **مالک یا اپراتور داشبورد** — شخص یا شرکتی که محصولات را در اختیار دارد و با
  این داشبورد دسترسی مشتریان را مدیریت می‌کند.
- **Tenant** — سازمان، کسب‌وکار یا حساب مشتری که دسترسی آن مدیریت می‌شود.
- **Service** — یکی از محصولات متصل مالک، مانند وب‌سایت کافه یا فروشگاه لباس.
  هر سرویس `serviceId` و کلید API مخصوص خود را دارد.
- **Plan** — تعریف تجاری قابل استفاده مجدد شامل قیمت، واحد پول، درگاه پرداخت،
  نوع پلن و مدت اعتبار.
- **Subscription** — اتصال یک tenant به یک plan. وضعیت چرخه عمر، تاریخ‌های
  اعتبار، کلید سریال، لغو و سوابق پرداخت در آن نگهداری می‌شود.
- **Flag** — قابلیت یا ویژگی قابل فعال‌سازی برای tenant، مانند
  `advanced_reports` یا `team_members`.
- **Entitlement** — پاسخ server-to-server که مشخص می‌کند tenant اجازه استفاده
  از سرویس را دارد یا نه و چه قابلیت‌هایی برای او فعال هستند.
- **Invoice و Payment** — سوابق مالی که پس از تأیید پرداخت توسط درگاه ایجاد
  می‌شوند. صرفاً برگشت مرورگر از درگاه باعث فعال شدن اشتراک نمی‌شود.

در مدل فعلی، هر tenant در هر لحظه یک subscription دارد. درخواست entitlement با
هر دو مقدار `tenantId` و `serviceId` محدود می‌شود تا سرویس‌ها نتوانند از کلید یا
اطلاعات سرویس دیگری استفاده کنند. وضعیت subscription در حال حاضر در سطح tenant
است؛ بنابراین تغییر وضعیت اشتراک یک tenant روی سرویس‌های متصل به همان tenant
اثر می‌گذارد.

### بخش‌های داشبورد

| بخش           | کاربرد                                                                           |
| ------------- | -------------------------------------------------------------------------------- |
| Overview      | نمایش MRR، تعداد اشتراک‌های فعال، صف dunning و فعالیت‌های اخیر.                  |
| Tenants       | ساخت و مدیریت مشتریان، ایمیل صورتحساب، وضعیت و جزئیات tenant.                    |
| Plans         | تعریف پلن‌های subscription یا serial key، قیمت، واحد پول، درگاه و مدت اعتبار.    |
| Subscriptions | مدیریت اتصال tenant به پلن، وضعیت چرخه عمر، بازه اعتبار، کلید سریال و پرداخت‌ها. |
| Services      | ثبت محصولات مالک، چرخش کلیدهای سرویس و تنظیم روش تحویل نتیجه پرداخت.             |
| Flags         | تعریف feature flag و فعال یا غیرفعال کردن آن برای tenant.                        |
| Audit         | بررسی فعالیت‌های مدیریتی، پرداخت، تغییر اعتبار و چرخه عمر.                       |
| Settings      | مشاهده تنظیمات عملیاتی و اطلاعات پیکربندی برنامه.                                |

کاربران OWNER و ADMIN داشبورد را مدیریت می‌کنند. کاربران TENANT متعلق به مشتری
هستند و به‌صورت پیش‌فرض به داشبورد مدیریت SaaS دسترسی ندارند.

### وضعیت‌های اشتراک و دسترسی

| وضعیت                    | معنی برای وب‌سایت متصل                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `ACTIVE`                 | دسترسی تا زمانی که بازه پلن معتبر باشد فعال است.                                             |
| `TRIALING`               | دسترسی در مدت آزمایشی فعال است.                                                              |
| `PAST_DUE`               | مشکل پرداخت ثبت شده، اما تا پایان بازه فعلی ممکن است دسترسی فعال بماند.                      |
| `GRACE_PERIOD`           | دسترسی غیرفعال است تا پرداخت موفق وضعیت را حل کند.                                           |
| `DISABLED`               | دسترسی غیرفعال است.                                                                          |
| `CANCELED`               | اشتراک لغو شده و از طریق پرداخت قابل فعال‌سازی مجدد نیست.                                    |
| `DISABLED_AT_PERIOD_END` | قبل از پایان بازه مانند فعال و پس از آن از نظر عملکردی غیرفعال است؛ مقدار status حفظ می‌شود. |
| `ARCHIVED`               | رکورد در APIهای entitlement و پرداخت مانند رکورد موجود رفتار نمی‌کند.                        |

فیلد `active` تصمیم اصلی برای اجازه دسترسی است. فیلدهای `status` و `reason`
اطلاعات تکمیلی هستند و می‌توان از آن‌ها برای نمایش پیام مناسب یا تصمیم‌گیری
درباره نمایش گزینه پرداخت استفاده کرد.

### روند پیشنهادی مالک یا اپراتور

1. هر محصول خود را در بخش **Services** ثبت کنید؛ مثلاً کافه، فروشگاه ورزشی و
   فروشگاه لباس را جداگانه ثبت کنید.
2. `serviceId` و کلید API تولیدشده هر سرویس را به توسعه‌دهنده همان محصول بدهید.
   کلید فقط هنگام ساخت یا تولید مجدد نمایش داده می‌شود.
3. پلن‌ها را در بخش **Plans** ایجاد و جزئیات درگاه را تنظیم کنید.
4. مشتریان را در بخش **Tenants** بسازید و برای آن‌ها subscription تعیین کنید.
5. توسعه‌دهنده در سمت سرور هر وب‌سایت، entitlement check را پیاده‌سازی کند.
6. وب‌سایت متصل بر اساس `active`، `status`، `reason` و `flags` دسترسی و محدودیت
   قابلیت‌ها را در طراحی خودش اعمال کند.
7. مالک از داخل داشبورد وضعیت اشتراک مشتری را تغییر دهد؛ مثلاً با غیرفعال کردن
   اشتراک، entitlement برای سرویس متصل غیرفعال خواهد شد.
8. در صورت نیاز، پرداخت و تمدید از طریق headless checkout انجام شود.

کلیدهای مشترک و کلیدهای سرویس را فقط در سمت سرور نگهداری کنید و آن‌ها را در
JavaScript مرورگر یا متغیرهای عمومی سمت کلاینت قرار ندهید.

### اتصال به Entitlement API

مسیر API:

```text
GET /api/v1/entitlements/:tenantId
```

Headerهای لازم:

```text
x-entitlement-secret: <shared entitlement secret>
x-service-id: <registered service id>
```

برای پلن‌های serial key، وب‌سایت می‌تواند کلید واردشده توسط مشتری را نیز ارسال
کند:

```text
x-serial-key: <customer-entered serial key>
```

نمونه پاسخ:

```json
{
  "active": true,
  "plan": "pro",
  "planType": "SUBSCRIPTION",
  "status": "ACTIVE",
  "reason": "ACTIVE",
  "periodEnd": "2026-10-19T12:00:00.000Z",
  "flags": {
    "advanced_reports": true
  }
}
```

در پلن serial key، API فقط وضعیت تطابق یا ثبت کلید را اعلام می‌کند و خود کلید
سریال را برنمی‌گرداند. tenant یا subscription آرشیوشده غیرفعال گزارش می‌شود و
اطلاعات رکورد آرشیوشده افشا نمی‌شود.

### ثبت Serial Key

برای ثبت کلیدی که مشتری وارد کرده است:

```text
POST /api/v1/entitlements/:tenantId
```

با همان headerهای احراز هویت و بدنه زیر:

```json
{ "serialKey": "customer-entered-key" }
```

این مقدار به‌صورت پایدار روی subscription ذخیره می‌شود؛ نه در cookie و نه در
متغیر محیطی. کلید اصلی تولیدشده از طریق entitlement API برگردانده نمی‌شود.

### پرداخت Headless

وب‌سایت متصل باید از سمت سرور checkout بسازد:

```text
POST /api/v1/payments/checkout
```

Headerها:

```text
x-service-id: <registered service id>
x-service-secret: <service-specific API key>
```

بدنه درخواست:

```json
{
  "tenantId": "<tenant id>",
  "serviceId": "<service id>",
  "planId": "<plan id>",
  "returnUrl": "https://product.example/payment-result"
}
```

پاسخ شامل URL درگاه و `checkoutId` است. مشتری را به URL درگاه هدایت کنید. فعال
شدن اشتراک فقط پس از تأیید webhook یا callback معتبر درگاه انجام می‌شود، نه
صرفاً با برگشت مشتری از درگاه.

پس از برگشت مشتری، وضعیت checkout را بررسی کنید:

```text
GET /api/v1/payments/checkouts/:checkoutId
```

و در صورت نیاز نتیجه پرداخت موفق را تحویل دهید:

```text
POST /api/v1/payments/checkouts/:checkoutId/deliver
```

روش تحویل در تنظیمات سرویس تعیین می‌کند که نتیجه از طریق callback، ایمیل یا هر
دو ارسال شود.

### وضعیت عملیاتی سرویس

سرویس‌ها در داشبورد برچسب‌های `HEALTHY`، `DEGRADED` و `OFFLINE` دارند. این‌ها
برچسب‌های عملیاتی مربوط به محصول هستند و فعلاً در پاسخ entitlement ارسال
نمی‌شوند. فیلد `active` درباره مجاز بودن دسترسی اشتراکی است، نه روشن یا خاموش
بودن خود وب‌سایت.

## اجرای پروژه

### اجرای محلی با Docker

```bash
cp .env.docker.example .env.docker
# مقادیر secret را در .env.docker تنظیم کنید.
npm run docker:deploy
npm run docker:ps
```

این دستور image نهایی را می‌سازد، PostgreSQL را اجرا می‌کند، migrationها را
اعمال می‌کند و TanStack Start را در حالت production بالا می‌آورد.

برای مشاهده لاگ‌ها:

```bash
npm run docker:logs
```

برای متوقف کردن stack بدون حذف داده پایگاه داده:

```bash
npm run docker:down
```

### اجرای توسعه

```bash
cp .env.example .env.local
npm install
npm run db:migrate
npm run db:seed:owner
npm run dev
```

### بررسی سلامت

```bash
curl -sS http://localhost:3000/api/health
```

پاسخ سالم:

```json
{ "ok": true, "database": "ok" }
```

### دستورات مهم

```bash
npm run format
npm run typecheck
npm run build
npm run test:security
npm run production:check
```

## نکات معماری

### Entitlement باید Server Route باشد

مسیر `src/routes/api/v1/entitlements/$tenantId.ts` عمداً یک server route است،
نه server function؛ زیرا وب‌سایت‌های متصل باید بتوانند آن را cross-origin صدا
بزنند. Server function برای کلاینت داخلی همین برنامه مناسب است و API پایدار
برای محصولات خارجی نیست.

### محل توسعه قابلیت‌ها

- قوانین کسب‌وکار را در `src/lib/` اضافه کنید، نه مستقیماً داخل کامپوننت UI.
- صفحات داشبورد را در `src/routes/_protected/` اضافه کنید.
- APIهای خارجی را در `src/routes/api/` اضافه کنید.
- دسترسی Prisma را فقط در سمت سرور نگه دارید.
- تغییرات schema را با migration نام‌گذاری‌شده انجام دهید.
- هر ترجمه جدید را در هر دو مسیر `src/i18n/en/` و `src/i18n/fa/` اضافه کنید.
- رفتارهای امنیتی جدید را با تست در `tests/security/` پوشش دهید.
- منطق providerهای پرداخت را در adapterهای `src/lib/payments/` نگه دارید.
